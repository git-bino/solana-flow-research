## 1. BigQuery dry_run — ГҮЙЦЭТГЭХ БОЛОМЖГҮЙ

**GCP хандалт байхгүй.** Шалгасан: `gcloud` байхгүй, `bq` байхгүй, `~/.config/gcloud/` байхгүй, `GOOGLE_*` / `GCLOUD_*` env var байхгүй. Тойрч гарах арга байхгүй — dry_run нь credential шаарддаг.

`bigquery-public-data.crypto_solana_mainnet_us` dataset нь **байгаа** (Solana Community × Google Cloud Public Datasets). Гэхдээ table-ийн бүтэц, partition багана нь юу болохыг **би батлаагүй** — таамаглаж query бичихээс татгалзаж байна. Тиймээс доорх алхмуудыг дарааллаар нь ажиллуулах шаардлагатай, гурвуулаа **үнэгүй**:

```bash
# 0) auth (интерактив, өөрөө ажиллуул)
gcloud auth login && gcloud config set project <PROJECT_ID>

# 1) ямар table байгааг харах — үнэгүй, metadata
bq ls --max_results 100 bigquery-public-data:crypto_solana_mainnet_us

# 2) instruction/лог агуулсан table-ийн schema, хэмжээ, partition багана — үнэгүй
bq show --schema --format=prettyjson bigquery-public-data:crypto_solana_mainnet_us.<TABLE>
bq query --use_legacy_sql=false --dry_run \
  'SELECT table_name, partition_column_name, total_logical_bytes/POW(10,12) AS tb
   FROM `bigquery-public-data.crypto_solana_mainnet_us.INFORMATION_SCHEMA.TABLES`'

# 3) dry_run — partition filter-тэй (pump.fun program id)
bq query --use_legacy_sql=false --dry_run \
  'SELECT COUNT(*) FROM `bigquery-public-data.crypto_solana_mainnet_us.<INSTRUCTIONS_TABLE>`
   WHERE <PARTITION_COL> BETWEEN "2026-05-10" AND "2026-08-15"
     AND program_id = "6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P"'

# 4) dry_run — partition filter-гүй (харьцуулалт)
bq query --use_legacy_sql=false --dry_run \
  'SELECT COUNT(*) FROM `bigquery-public-data.crypto_solana_mainnet_us.<INSTRUCTIONS_TABLE>`
   WHERE program_id = "6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P"'
```

`--dry_run` нь `totalBytesProcessed`-ыг буцаана. Зардал = TB × $6.25, сарын **эхний 1 TB үнэгүй**. `program_id = 6EF8rre...` нь pump.fun-ийн program address — Dune-ийн `evt_executing_account` баганаас баталгаажсан (дээжийн бүх мөр дээр ижил).

**Decode-ын ажлын үнэлгээ (миний инженерийн үнэлгээ, хэмжилт биш):**

| Хэсэг | Хугацаа | Эрсдэл |
|---|---|---|
| Anchor event discriminator + `TradeEvent` struct-ыг unpack (borsh, 8-байт discriminator, u64/bool/pubkey талбарууд) | 0.5 хоног | **Бага** — layout нь IDL-д тодорхой, Dune-ийн decoded мөртэй тулгаж баталж болно |
| CPI event log-ыг гаргаж авах (pump.fun event-үүд `invoke`-ийн inner instruction дотор base64 log хэлбэрээр гардаг) | 1 хоног | **Дунд** — log-ийн формат program version-оор хувирдаг; таслагдсан log (`log truncated`) байвал event алдагдана |
| `CreateEvent` (universe) + `CompleteEvent`/migration | 0.5 хоног | Бага |
| Program version 2-ын шинэ талбарууд (`fee`, `creator_fee`, `quote_mint`, `mayhem_mode`, `virtual_*`) | 0.5 хоног | **Дунд** — layout нь v1/v2-т өөр, discriminator-оор салгах ёстой |
| Dune-ий 3 хоногийн дээжтэй мөр мөрөөр тулгах баталгаажуулалт | 1 хоног | **Хамгийн үнэ цэнтэй хэсэг** — Dune-ийг ground truth болгож 6.6M event дээр тулгавал decode-ийн зөв эсэх нь тоогоор батлагдана |
| **Нийт** | **3.5–4 хоног** | Гол эрсдэл: log truncation ба version layout |

Нэг бодит давуу тал: event struct-ыг өөрөө уншвал **§0.3-ийн fee-ийн тодорхойгүй байдал үүсэхгүй** — гэхдээ доорх хэмжилт 4 үүнийг Dune дээр аль хэдийн шийдчихсэн тул энэ давуу тал одоо үнэ цэнээ алдсан.

|---|---|---|---|---|---|---|---|---|

| **≥1 burst (0.10×x, 2s)** | **28,251** | **37.8%** | **5,169,072** | **78.0%** | 155,072,160 | 26,952 | 539,045 | **0.390%** |

**Гол тоо: burst үүсгэдэг токенууд нь токений 37.8% боловч event-ийн 78.0%.** Тиймээс burst-гүй токенуудыг хассан ч credit-ийн зардал **зөвхөн 22% буурна** (691,084 → 539,045). Free-д багтах түүвэр 0.286%-аас 0.390% болно — **1.36 дахин**, шаардлагатай 35 дахин биш.

Сервер дээр хэрэгжүүлэх боломжтой сул хувилбар (`max net_flow_2s ≥ 1 SOL`) нь бүр дор: 89.4% event үлдэнэ.

> Энэ нь **§2.2-ийн universe дүрмийг өөрчлөх санал биш** — зөвхөн тоо. Хэрэв судалгааны нэгж burst event бол burst-гүй токен тоололд тэг мөр оруулна гэдэг чиний тайлбар зөв; гэхдээ тоонууд нь энэ чиглэлээр Free plan-ыг аврахгүй гэдгийг харуулж байна.

**mayhem нь launch дээр тогтоогддог, дараа олж авдаггүй.** Онсетийн median 0 секунд — өөрөөр хэлбэл токений *хамгийн эхний арилжаа* аль хэдийн mayhem туг зүүсэн байна. 153 секундын max нь mayhem авсан хамгийн хожуу *эхний арилжаа* — mayhem авсан мөч биш.

**Тиймээс чиний тавьсан survivorship-ийн асуулт шууд хариулагдаж байна:** идэвх нь mayhem-ийг үүсгэх боломжгүй, учир нь туг нь **арилжаа үүсэхээс өмнө** тавигдсан байдаг. Mayhem-ээр шүүх нь ирээдүйн мэдээлэл ашиглахгүй, мөн real-time-д хэрэгжих боломжтой (launch дээр л мэдэгдэнэ → §12.1-ийн Давхарга 0-д таарна).

## 4. Reserve багана байгаа эсэх — БАЙГАА, бөгөөд цуваа нь бүтэн

`information_schema`-аар шалгах шаардлага байхгүй: Dune-ийн decoded pump.fun table-ууд **`information_schema`-д байдаггүй** (яг тэр query 0 мөр буцаасан, өмнөх нь LIKE-тайгаа 180 credit авсан), харин `SELECT * LIMIT 1` дээжээс баганууд шууд харагдсан:

`pumpdotfun_solana.pump_evt_tradeevent` дээр арилжааны **дараах** төлөв:
`virtual_sol_reserves`, `virtual_token_reserves` — судалгааны цонхны **100% мөр дээр бөглөгдсөн** (2,404,573 / 2,404,573 6-01-нд), мөн `real_sol_reserves`, `real_token_reserves`, `fee`, `creator_fee`, `fee_basis_points`.
`pump_evt_createevent` дээр **токен тус бүрийн эхлэлийн** төлөв: `virtual_sol_reserves = 30000000000`, `virtual_token_reserves = 1073000000000000`, `real_token_reserves = 793100000000000`.

### Цуваа нь curve-ийн ижилтгэлийг дагаж байна уу — 6,551,088 дараалсан хос дээр (бүхэл `decimal(38,0)` арифметик, float биш)

| | mayhem БИШ | mayhem |
|---|---|---|
| Хос | 5,132,812 (78.3%) | 1,418,276 (21.7%) |
| `Δvsol = ±sol_amount` яг таарсан | **100.0000%** | 41.79% |
| `Δvtoken = ∓token_amount` яг таарсан | **100.0000%** | **100.0000%** |
| Хоёр тал хоёулаа | **100.0000%** | 41.79% |
| `\|Δ(x·y)/(x·y)\|` median | 8.4×10⁻¹² | 7.4×10⁻² |
| p90 / p99 / max | 2.5e-11 / 3.3e-11 / **3.3×10⁻¹¹** | 0.287 / 0.462 / **4.40** |

**Гурван дүгнэлт:**

**(1) §0.3 хариулагдсан: `sol_amount` нь NET (шимтгэлгүй).** Mayhem биш 5.13M хос дээр `Δvsol = ±sol_amount` **яг** таарсан. "Gross" таамаглал (`sol_amount − fee − creator_fee`) 1.47% дээр л таарсан. Мөн **74,733 / 74,733 = 100%** токений эхний арилжаа NET таамаглал дор `x₀ = 30 SOL`-ыг яг гаргасан (gross дор 0). `fee` ба `creator_fee` нь тусдаа багана — curve-ээс гадуур. §0.3-ийн 3 алхам бүрэн: тодорхойлсон (арифметикээр, баримтжуулалтаар биш), бичсэн (энд), reconstruction-той нийцсэн (доорх (3)).

**(2) mayhem биш токенууд дээр constant-product **яг** биелж байна.** `x·y` нь 3.3×10⁻¹¹-ээс их хэзээ ч хазайгаагүй — энэ нь цэвэр бүхэл тооны truncation. Абсолют дүнгээр ~115 SOL × 3.3e-11 ≈ **4×10⁻⁹ SOL**, шалгалт 1-ийн 0.01 SOL босгоос **6 дэс** дотор.

**(3) mayhem токенууд constant-product-ыг дагахгүй.** SOL тал 58%-д таарахгүй, `x·y` нь арилжаа тутам median **7.4%**, max 440% хувирдаг. Token тал үргэлж таардаг тул **virtual SOL (quote) reserve нь дахин параметржиж байна** — program-ийн `set_virtual_quote_reserves` instruction-ийн нэр яг үүнийг хэлж байна. Энэ нь алдаа биш, өөр механизм.

### Шалгалт 1-ийн kill criterion-д шууд нөлөө

| Хамрах хүрээ | `Δvsol` таарах хувь | Шалгалт 1 (>99% босго) |
|---|---|---|
| Бүх токен | **87.40%** | **FAIL** |
| mayhem биш токенууд | **100.00%** | **PASS** (зөрүү ~4×10⁻⁹ SOL) |

Өөрөөр хэлбэл **kill criterion-ий үр дүн нь mayhem-ийн хамрах хүрээний шийдвэрээс бүхэлдээ хамаарна** — датаг татахаас өмнө мэдэгдэж байна. Энэ бол Phase 0-ийн гол утга.

### Санал (хэрэгжүүлээгүй, чиний шийдвэрийг хүлээж байна)

**Санал A — `x_pre`/`x_post`-ыг replay хийхгүй, уншина.** `virtual_sol_reserves` нь арилжааны дараах төлөв тул `x_post` шууд уншигдана; `x_pre = x_post − (±sol_amount)` нь нэг мөрийн дотор бодогддог, өмнөх түүхээс хамаарахгүй. Давуу тал: (а) event дутсан ч дараагийн event-үүд бохирдохгүй (одоогийн cumulative replay нь нэг цоорхойноос хойш бүх мөрийг унагана), (б) mayhem-ийн үсрэлт **алдаа биш, тэмдэглэгдсэн үйл явдал** болно, (в) арифметик нь мөр тус бүрд локал тул lookahead-ийн эрсдэл бүрмөсөн байхгүй.

**Санал B — шалгалт 1-ийг дараах байдлаар өөрчлөх** (spec §7 Phase 0-ийн засвар, чи батлах):

> **1a. Цувааны бүтэн байдал:** `vsol_post[i+1] − vsol_post[i] = ±sol_amount[i+1]` ба `vtoken_post[i+1] − vtoken_post[i] = ∓token_amount[i+1]`, токен бүр дотор, event-ийн >99% дээр. (Одоо: mayhem биш дээр 100%.)
> **1b. Curve-ийн ижилтгэл:** `|Δ(x·y)/(x·y)| < 10⁻⁹`, event-ийн >99% дээр. (Одоо: mayhem биш дээр 100%, max 3.3e-11.)
> **1c. Эхлэлийн төлөв:** токений эхний арилжааны `x_pre` нь тэр токений `createevent`-ийн `virtual_sol_reserves`-тэй тэнцүү. (Одоо: 100%.)

Хуучин "replay vs on-chain" шалгалт нь `Δvsol = ±sol_amount` (1a)-тай математикийн хувьд ижил зүйлийг хэмждэг, гэхдээ cumulative хэлбэрээр — тиймээс 1a нь ижил хүчтэй, харин ямар event дээр буруудсаныг **тухайн мөрөнд** зааж өгдөг. §0.4-ийн Decimal/float асуудал ч мөн адил алга болно: cumulative нийлбэр байхгүй бол хуримтлагдах алдаа ч байхгүй.

**Санал C — `y₀` ба `k`-г токен тус бүрийн `createevent`-ээс унших**, spec §1.1-ийн глобал тогтмолын оронд. Эмпирик: 81,052/81,052 токен `y₀ = 1,073,000,000` (spec-ийн 1,073,000,191 нь 0 токен дээр), `x₀ = 30 SOL` бүгд дээр. Токен тус бүрээс уншвал ирээдүйд параметр өөрчлөгдөхөд код өөрөө засагдана.
