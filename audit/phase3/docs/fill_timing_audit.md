## 0. Урьдчилсан баримт: `virtual_sol_reserves` нь trade-ийн ДАРААХ нөөц

Энэ нь §1 ба §2-ын бүх хариуг тодорхойлно, тиймээс эхлээд **баталсан, таамаглаагүй**.

`sql/phase0_kill_gate.sql:90-95` нь `x_pre`-г **хасалтаар** гаргана:

```sql
-- 1c: the first trade of every token, and the reserve it started from.
firsts AS (
    SELECT mint,
           if(is_buy, vsol - lam, vsol + lam) AS x_pre_first
    FROM seqd
    WHERE seq = 1
),
```

`sql/phase0_kill_gate.sql:163` нь түүнийг **яг 30 SOL** эсэхийг шалгана:

```sql
    (SELECT count_if(x_pre_first = 30000000000) FROM firsts)         AS c_first_at_30sol,
```

**Бүртгэгдсэн үр дүн** (`results/phase0_measurements.md:133`):
**74,733 / 74,733 = 100%** токений эхний арилжаа NET таамаглал дор `x₀ = 30 SOL`-ыг **яг** гаргасан.

Хэрэв `virtual_sol_reserves` нь ӨМНӨХ утга байсан бол buy дээр `vsol − lam = 30 − lam ≠ 30` болох
байсан. **Иймд `virtual_sol_reserves` нь ДАРААХ (post-trade) нөөц.**
`sql/extract_v2.sql:128` дээрх `x_sol = vsol/1e9` → `depth_x` (мөр 501) мөн post-trade утга.

## 1. Орох цэг

### 1а. Ledger нь анкор event-ийг ОРУУЛЖ тоолдог — SQL-ийн мөрөөр

`sql/holder_anchor.sql:86-89` — түрийвч тутмын үлдэгдэл нь **одоогийн мөрийг оруулна**:

```sql
    SELECT mint, seq, w, sl, bt, x, du,
           sum(du) OVER (PARTITION BY mint, w ORDER BY seq
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS b
    FROM legs2
```

`:93-97` — шилжилт нь `b` (дараах) ба `b − du` (өмнөх) хоёрыг харьцуулна:

```sql
           sum(CASE WHEN b > 0 AND b - du <= 0 THEN 1
                    WHEN b <= 0 AND b - du > 0 THEN -1
                    ELSE 0 END) AS d
```

`:100-101` — эзэмшигчийн тоо мөн **одоогийн мөрийг оруулна**:

```sql
           sum(d) OVER (PARTITION BY mint ORDER BY seq
                        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS nh,
```

`:112` — анкор нь `nh >= 3` анх болсон мөр:

```sql
    FROM hc WHERE nh >= 3 GROUP BY mint
```

→ **`n_holders = 3` нь тэр event ДУУСМАГЦ үнэн болно.** Анкор event нь тоололд орсон. ✓

### 1б. `x_a` нь анкор event-ийн ДАРААХ `x`

`sql/holder_anchor.sql:104-105` ба `:111`:

```sql
           last_value(x) IGNORE NULLS OVER (PARTITION BY mint ORDER BY seq
                        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS x_ff
...
           min_by(x_ff, seq) AS x_a, min_by(nh, seq) AS nh_a
```

`x` нь `:51` дээр `CAST(t.virtual_sol_reserves AS bigint) / 1e9` — §0-оор **post-trade**.
Цонх нь `CURRENT ROW` хүртэл → `x_ff` нь анкор event-ийн **өөрийнх нь дараах** нөөц.
(Анкор нь transfer байвал transfer нь нөөцийг хөдөлгөдөггүй тул carry-forward нь зөв утга өгнө.)

→ **`x_a` = анкор event ДУУССАНЫ ДАРААХ `x`. Хүршгүй үнэ БИШ.** ✓

### 1в. Хамгийн эрт executable fill

Анкорын нөхцөл нь event дуусмагц мэдэгдэнэ → хамгийн эрт транзакц нь **дараагийн event**.
Тэр транзакцийн эхлэх нөөц нь яг `x_a`. `sql/asymmetric_barriers.sql:53` нь урагшлах олонлогийг
**хатуу дараа** гэж тодорхойлно:

```sql
    FROM a JOIN ev e ON e.mint = a.token_mint AND e.seq > a.seq_a
```

→ **Одоогийн код нь дараагийн event дээр орж байна** (үнэ нь анкорын дараах нөөц, хайлт нь
`seq > seq_a`). ✓ **Нэг event-ийн lookahead БАЙХГҮЙ.**

### 1г. Хэрэв `x_a` нь ӨМНӨХ утга байсан бол — тоогоор

`x_a` нь ӨМНӨХ утга **биш** тул энэ нь согогийн хэмжээ биш, **мэдрэмжийн** тоо:
«хэрэв нэг event-ээр эрт үнэлсэн бол хэдий хэмжээний хиймэл ашиг гарах байсан бэ».

H3 анкор event-ийн өөрийнх нь `x`-хөдөлгөөнийг локал дээр **гаргах боломжгүй** (анкорын
арилжааны хэмжээ локал дата дотор алга — §3-ыг үзнэ үү). Локал дээр байгаа хамгийн ойр
хэмжилт нь `flow.burst_v2`-ийн **trigger event** (126,089 мөр, mayhem бус). `sol_amount` нь
NET болох нь phase0 §0.3-д батлагдсан тул `x_pre = depth_x ∓ trigger_sol`:

| хэмжилт | p50 | p90 | p99 | max |
|---|---|---|---|---|
| trigger event-ийн өөрийн хөдөлгөөн `\|trigger_sol\| / depth_x` | **4.434%** | 14.286% | 33.058% | 73.9% |
| SOL-оор `\|trigger_sol\|` | 1.7507 | 5.0000 | — | — |
| **үнийн хиймэл ашиг** `(x_post/x_pre)² − 1` (buy trigger) | **+9.595%** | **+36.111%** | +123.15% | — |

Харьцуулалтад **хуучин согогийн зай** `(x_end_slot − depth_x)/depth_x`:
p50 **2.049%**, p90 16.948%, p99 53.382%; тэгээс ялгаатай нь мөрийн **72.32%**.

> **⚠ ХАЗАЙЛТ ИЛ:** burst trigger нь бүтцийн хувьд **том** арилжаа (`nf5 ≥ max(3, 0.10·x)`),
> H3 анкор нь ихэвчлэн **жижиг эрт худалдан авалт**. Иймд дээрх тоо нь H3 анкорын хөдөлгөөний
> **дээд талын тооцоо**, шууд орлуулга **биш**.

## 2. Гарах цэг

### 2а. Гарах fill нь давалтын event-ийн ДАРААХ нөөц дээр

`sql/asymmetric_barriers.sql:61-63` (жишээ, `−20%` зогсоол):

```sql
       min(if(x <= x_a * 0.8, sl))                       AS sl_d20,
       min_by(x,  if(x <= x_a * 0.8, seq))                AS x_d20,
       min(if(x <= x_a * 0.8, ut)) - max(anchor_unix)     AS t_d20,
```

`min_by(x, if(cond, seq))` нь **нөхцөлийг хангасан хамгийн эрт event-ийн `x`**-ийг өгнө
(Trino-д түлхүүр NULL байх мөрүүд алгасагдана). `x` нь дахин post-trade.

→ **Гарах үнэ = давалтын event ДУУССАНЫ ДАРААХ нөөц.** Орох талтай **тэгш хэмтэй**. ✓

### 2б. Хадгалсан overshoot нь давалтын event-ийн ДАРААХ `x` мөн

Тийм — `:44` дээрх `x` нь post-trade, `min_by` нь тэр утгыг сонгоно. Ажиглагдсан:
win талд бодит/босго median **1.0250 … 1.0534**, loss талд **0.9367 … 0.8925**
(`docs/asymmetric_barriers.md` §4).

### 2в. Давалтын event дээрээ гардаг уу

**Үгүй — түүний ДАРААХ нөөц дээр гарна**, өөрөөр хэлбэл давалт болсныг мэдсэний дараа
хамгийн эрт транзакц. Нэг event-ийн lookahead **байхгүй**.

`sql/asym_passage.sql:86` нь орох/гарах хоёрыг **ижил суурьтай** харьцуулна:

```sql
           CASE WHEN win THEN xt/x_a  WHEN loss THEN xs/x_a  ELSE final_x/x_a END AS r_ovr
```

Хуанли: `x_a` (анкорын дараах) ба `xt` / `xs` (давалтын дараах) — **хоёулаа post-event**.
Хуучин согог нь энэ хоёрыг **өөр түвшинд** (мөр vs slot) авсанд байсан.

## 3. Хоёр согогийг засаад дахин тооцох

**СОГОГ ИЛРЭЭГҮЙ.** §1 ба §2-ын аль алинд нь орох/гарах хоёулаа **event дууссаны дараах**
нөөц дээр үнэлэгдэж байгаа бөгөөд урагшлах хайлт нь `seq > seq_a` буюу **хатуу дараа**.
Даалгаврын §3 нь «Хэрэв 1 эсвэл 2-т согог илэрвэл» гэсэн **нөхцөлт** тул дахин тооцоолол
**шаардлагагүй** — өмнөх тоонууд хэвээр.

### Юуг локал дээр хийх БОЛОМЖГҮЙ, ямар query хэрэгтэй

§1г-ийн бүрэн хариу (H3 анкор event-ийн өөрийн `x`-хөдөлгөөний тархалт) нь анкор event-ийн
**арилжааны хэмжээ ба чиглэл** шаардана. `result_flow_holder_anchor` нь `seq_a` ба `x_a`-г
хадгалдаг ч `sol_amount` / `is_buy`-г хадгалдаггүй; локал ClickHouse-д зөвхөн `burst_v2` бий
(`flow.event` **0 мөр**).

> **АСУУЛТ УДИРДАГЧИД (өөрөө шийдээгүй, ажиллуулаагүй):**
> H3 анкор дээрх `x_before`-ыг гаргахын тулд `result_flow_holder_anchor`-ыг `tradeevent`-тэй
> `seq = seq_a` дээр join хийж `sol_amount`, `is_buy`-г татах query хэрэгтэй.
> **Зардлын тооцоо: ~4 credit** (11 хоногийн scan + 153,092 анкорын яг таарах join; анкор
> `path_dist_at_level` = 7.979 cr нь 3 дахин өргөтгөлтэй байсан, энэ нь өргөтгөлгүй).
> **× 3 = 12.** Ажиллуулах уу?
