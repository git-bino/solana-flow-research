# `oh_a`-ийн parity зөрүүний оношлогоо

**Огноо:** 2026-08-20 · **0 credit зарцуулсан** (бүх ажил локал) · Бюджет 60-аас 0
**Extract ажиллуулаагүй · materialization хийгээгүй · Phase 3b рүү ороогүй · ЗАСААГҮЙ**

## Товч хариу

> **Wallet `W` дээр, үлдэгдлийг СӨРӨГ хэвээр үлдээсэн BUY event-ийн дараа SQL нь тэр
> buy-г cost basis-аас ХАЯДАГ, Python нь ХАДГАЛДАГ.** Шалтгаан: SQL-ийн segment
> тоолуур `held ≤ 0` болсон **аливаа** мөрийн дараа өсдөг (талыг үл харгалзан), Python
> нь `held ≤ 0`-ийг **зөвхөн sell салаанд** шалгадаг.

`held_units` хоёр талд **яг таарна**; зөрүү нь бүхэлдээ `cb`-д.

## Аргачлал — SQL-ийг локалаар эмуляцлав

Dune руу дахин хандахгүйн тулд `sql/extract_v2.sql`-ийн ledger-ийн семантикийг
(`pos → run → segd → wstate → wat → contrib → oh`) Python дээр эмуляцлав. Эмуляцийн
үнэн зөвийг **хэмжсэн**:

| тулгалт | зөрөх | max \|Δ\| |
|---|---|---|
| эмуляцийн `oh_a` ↔ SQL-ийн `oh_a` (2 зөрөх мөр дээр) | **0 / 2** | < 1e-6 |
| эмуляцийн `cb_reset_gross` ↔ SQL (бүх мөр) | **0 / 88** | **1.540e-23** |

Эмуляц SQL-ийг давтаж байгаа тул доорх бүх дүгнэлт нь SQL-ийн бодит зан төлөвийн тухай,
таамаг биш.

## 3. Хоёр талын дүрмийн яг ялгаа

```
SQL   seg_id = sum(if(held <= 0, 1, 0)) OVER (… ROWS UNBOUNDED PRECEDING AND 1 PRECEDING)
      → `held ≤ 0` болсон ЛЮБОЙ мөрийн ДАРААХ мөр шинэ segment эхэлнэ,
        тэр мөр buy байсан ч ялгаагүй.

PY    WalletStateV2.apply_trade:
          if ev.is_buy:  … (шалгалт БАЙХГҮЙ)
          else:          held -= units;  if held <= 0: _reset()
      → зөвхөн SELL нь reset хийнэ.
```

### Хилийн тохиолдлууд, тестээр барьсан (`tests/test_basis_reset_boundary.py`)

|---|---|---|---|

Сүүлийн хоёрын эхнийх нь бодит зөрүүг бүрэн тайлбарлана. Хоёр дахь нь ижил дүрмийн нэг
мөр өмнөх илрэл — тэр мөрөнд wallet юу ч барихгүй тул OH-д нөлөөлөхгүй.

## 4. `cb_reset_gross`-ийн тулгалт — like-for-like болгосон

Өмнөх тайланд «тулгалт like-for-like биш байж болзошгүй» гэж тэмдэглэсэн. **Тэр
таамаг буруу байв:** нэгтгэлийн нэгжийг SQL-тэй яг ижил болгож (burst-ийн агшинд, ижил
wallet олонлог дээр `sum(seg_lam)/(sum(seg_units)·1000)`) дахин хэмжихэд:

| | зөрөх | max \|Δ\| |
|---|---|---|
| өмнөх тулгалт | 29 / 88 | 2.658e-8 |
| **ижил нэгж дээр дахин** | **29 / 88** | **2.658e-8** |

**Өөрчлөгдөөгүй** — зөрүү бодит. `oh_a`-ийн 3 мөрөөс олон байгаа нь `cb_reset_gross` нь
**бүх wallet дээр** нэгтгэгддэгтэй холбоотой: OH-д хувь нэмэр оруулаагүй (cb ≥ P эсвэл
units = 0) wallet ч энд тусна. **Шалтгаан нь ижил** — сөрөг үлдэгдэл дээрх buy.

## 5. Энэ нь яагаад огт үүсдэг вэ

Сөрөг үлдэгдэл нь **curve дээр боломжгүй**. Тэр нь зөвхөн **ledger-ийн харагдахгүй SPL
transfer**-ээс үүснэ: хүлээн авагч нь өөрийн авч байгаагүй токеныг зарахад ledger нь
сөрөг рүү орно. Хэмжсэн тархалт: **(wallet, token) хосын 2.371%**, 182 токений **51**-д
(`docs/audit_mechanism_prevalence.md`). Өөрөөр хэлбэл энэ parity зөрүү нь аль хэдийн
мэдэгдэж буй датаны согогийн **урсгал доорх үр дагавар**.

## Шийдэх ёстой асуулт — spec-ийн, кодын биш

§1.2 нь cost basis-ыг **buy-жинтэй дундаж** гэж тодорхойлж, sell нь түүнийг хөндөхгүй
гэж заасан. Сөрөг үлдэгдлийн тухай **юу ч хэлээгүй** — тийм төлөв curve дээр байх
боломжгүй тул. Тиймээс:

- SQL-ийн дүрэм («сөрөг үлдэгдэл дээрх buy нь шинэ позиц эхлүүлнэ») ч,
- Python-ийн дүрэм («зөвхөн sell нь позицийг хаана») ч

**§1.2-оос гарахгүй.** Аль нь зөв болохыг **spec тодорхойлох ёстой**, кодын аль нэг тал
биш. **ЗАСААГҮЙ, шийдвэрийг судалгааны удирдагчид үлдээв.**

Хэмжигдсэн нөлөө: `oh_a` дээр **2 / 88 мөр**, max **0.914 SOL (0.3%)**;
`cb_reset_gross` дээр **29 / 88 мөр**, max 2.658e-8 SOL/токен.
