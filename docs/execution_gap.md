## 0. Бүтэц ба хоёр засвар

`result_flow_hbar` нь давалтын **slot**-ыг хадгалдаг ч `seq`-ийг биш, мөн анкороос хойших
k-дахь event-ийг огт хадгалдаггүй → **шинэ forward pass зайлшгүй**.

**Window ашиглаагүй.** `min_by(x, seq, 8)` нь хамгийн бага 8 `seq`-д харгалзах `x`-ийн
**массивыг** буцаана — анкороос хойших эхний найман event, дараалалтайгаа, хязгаарлагдмал
санах ойн агрегатаар. `row_number()` window нь ~9M мөрийг токеноор эрэмбэлэх байсан
(тийм хоёр эрэмбэлэлт `result_flow_holder_anchor`-д **24.466 cr** авсан).
**ЭНЭ БОЛ CLAUDE CODE-ИЙН ШИЙДВЭР** — зардлын инженерчлэл; саатлын тодорхойлолт даалгаврынхаар хэвээр.

### ⚠ Миний хоёр согог, зассан

1. **`percent_rank()` нь NULL мөрүүдийг эрэмбэлдэг.** 8-event саатал дээр мөрийн **26.11%**
   огт дүүрдэггүй (`ret` NULL) тул trim1/trim5/trim10 бүгд NULL блокийн дотор унаж,
   гурвуулаа дундажтай **яг тэнцүү** гарч байсан. Засвар: `PARTITION BY …, (ret IS NULL)`.
2. **Саатал тутам ӨӨР популяци харьцуулагдаж байсан.** Урт саатал дээр хасагдаж буй мөрүүд нь
   **хурдан үхсэн** токенууд — санамсаргүй дэд олонлог биш. Тиймээс `common8` багана нэмж,
   **бүх саатал дээр дүүрдэг** мөрүүд (8 дахь event-тэй) дээрх дундажийг тусад нь гаргав.

e3 дээр **−3.12%**; realistic дээр **−9.01%**. `creator c1 × 3–10 с`, `+76%`: **+7.03% → −5.74% → −9.01%**.
Саатал 0 дээр trim5 эерэг байсан **8 нүд-зорилт** нь e3 дээр **бүгд сөрөг** болно.

**Нийт популяци дээр саатал өгөөжийг ТОГТМОЛ БУУРУУЛНА** (энэ нь зөв харьцуулалт):
`creator c1 × 3–10 с`, `+76%`: e0 **+33.49%** → e3 **+29.72%** → e8 **+30.11%**;
`+135%`: e0 **+58.48%** → e3 **+51.75%** → e8 **+48.15%**.
«Бүх» баганад e8 нь **өндөр** харагддаг (+6.71 … +14.48 пункт) нь зөвхөн 26.11%-ийн
**хасалтын сонголт**.

**Гарах талын саатал өгөөжийг ӨСГӨНӨ:** `e0 × гарц 3` нь бүх нүдэнд e0-ээс **+6.47 … +7.12 пункт**
өндөр — давалтаас хойш гурван event хүлээхэд дундаж гарах нөөц үргэлжлэн өсдөг.
Realistic (орох 3 × гарц 3) нь тэр хоёрын нийлбэр: **+3.60 … +8.36 пункт** e0-ээс дээгүүр
(бүх популяци дээр), гэвч **trim5 бүгд сөрөг**.
