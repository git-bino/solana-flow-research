# Phase 1 — Зардлын загвар, reserve-ийн яг замаар

**Огноо:** 2026-08-19 · `src/cost_model.py` · `tests/test_cost_model.py`
**Dune-д хандаагүй** (үлдэгдэл 26.84) · **extract хийгээгүй** · **Phase 3b рүү ороогүй** · **шийдвэр гаргаагүй**

## Юуг яагаад сольсон

Гадаад аудит §1.1-ийн `BE = (1+V/x)²(1+q/x)²(1+fees) − 1`-ийг буруу гэж тогтоов
(decisions.md, 2026-08-19). Эсрэг жишээ: `V = 0`, `fees = 0` үед `q` SOL-оор аваад
тэр даруй буцааж зарвал constant product дээр reserve `x → x+q → x` болж gross P&L
**яг тэг**. Гэтэл томьёо `(1+q/x)² − 1 > 0` зардал гаргана — **өөрийн impact round
trip дээр хоёр удаа алдагдал болж тоологдсон**, гарахдаа буцаагдахыг тооцоогүй.

Томьёо v1.0-оос хойш байсан ба **kill criterion (ii) түүн дээр тогтдог**.
Хуучин хэрэгжүүлэлт `src/curve.py`-д **хасагдаагүй**: `breakeven_legacy` болж нэрлэгдээд
deprecated тэмдэглэгдсэн (Phase 3a-ийн тоонуудыг он цагт нь тавихад хэрэгтэй).

## Гаргалт, алхам тутам

Тэмдэглэгээ: `k = x₀·y₀` тогтмол; аливаа reserve `x` дээр `y = k/x`.
`x` нь SOL, `y` нь токен, тиймээс `k` нь SOL·токен.

```
1. Ажиглалт          reserve = x_obs
2. Хоцролт           V SOL цэвэр урсгал чиний өмнө land хийнэ
                     x₁ = x_obs + V
3. Чиний buy         q SOL curve-д орно (шимтгэлийн ДАРААХ)
                     Δy = k/x₁ − k/(x₁+q)          ← авах токен
                     x_e = x₁ + q
4. Дараагийн урсгал  W SOL цэвэр   ← ХАЙЖ БУЙ ХЭМЖИГДЭХҮҮН
                     x₂ = x_e + W
5. Чиний exit        y_state = k/x₂ ;  зарсны дараа y = y_state + Δy
                     x_f = k/(y_state + Δy)
                     gross SOL out = x₂ − x_f
```

`x_f`-ийг задлавал `x_f = k·x₂/(k + Δy·x₂)`, тиймээс

```
gross SOL out = x₂ − k·x₂/(k + Δy·x₂) = Δy·x₂² / (k + Δy·x₂)
```

Энэ хэлбэрээр бичсэн шалтгаан: хоёр том reserve-ийн ялгавар нь хасалт дээр
нарийвчлалаа алддаг.

**Шимтгэл.** pump.fun 95bp + creator 30bp = **1.25% тал тутамд** (§1.1, §5).
Entry дээр `q` нь curve-д ороход NET, тиймээс түрийвчнээс `q/(1−f)` гарна.
Exit дээр curve `x₂ − x_f` төлж, түрийвчинд `(x₂ − x_f)·(1−f)` үлдэнэ.
Priority fee / tip нь `pf` SOL, тал тутамд.

```
net P&L = (x₂ − x_f)·(1 − f) − q/(1 − f) − 2·pf
```

### Шалгалт: аудитын эсрэг жишээ

`V = 0, W = 0, f = 0, pf = 0` үед `x₂ = x_obs + q`,
`y_state + Δy = k/(x_obs+q) + k/x_obs − k/(x_obs+q) = k/x_obs`,
тиймээс `x_f = x_obs` ба gross out `= q`. **net P&L = q − q = 0, яг тэг.** ✓

## `breakeven_W` — ХААЛТТАЙ ХЭЛБЭР, root-finding ашиглаагүй

Шаардагдах gross орлого:

```
R = (q/(1−f) + 2·pf) / (1−f)
```

`Δy·x₂²/(k + Δy·x₂) = R` → `Δy·x₂² − R·Δy·x₂ − R·k = 0` → эерэг үндэс:

```
x₂ = [ R + √(R² + 4·R·k/Δy) ] / 2
W  = x₂ − x_e
```

**Аль замыг сонгосон:** хаалттай хэлбэр. `Decimal.sqrt` нь ажлын нарийвчлалд яг
бөгөөд brentq-ийн 1e-12 SOL-ын хүлцлээс хамаагүй сайн. Алгебрт итгэхийн оронд
тест 7 нь `net_pnl(W = BE_W) = 0`-ыг **лавлагаа хүснэгтийн 96 нүд бүрд** орлуулж
шалгана.

**Арифметик `Decimal`, 60 орон.** float64 дээр `k/x₁ − k/(x₁+q)` хасалт хийгээд
`k/(x₁+q)`-г буцааж нэмэхэд ~1e-14 SOL дуу чимээ үлдэнэ — аудитын эсрэг жишээнд
шаардагдах 1e-15-аас том.

`k`-ийн анхдагч: `x₀ = 30 SOL`, `y₀ = 1,073,000,000 токен` (§1.1-ийн эмпирик утга,
81,052/81,052 токен) → `k = 3.219e10`.

## Юу харагдаж байна

- **`W`-ийн хамаарал `q`-аас сул.** `x = 35` дээр `q` нь 0.5 → 5 болоход (10 дахин)
  `W` нь 0.4526 → 0.5405 л болно (+19%). Учир нь өөрийн impact гарахдаа
  буцаагддаг — үлдэх зардал нь зөвхөн шимтгэлийн `q`-тай пропорциональ хэсэг.
  Хуучин томьёо энэ хамаарлыг эрс хэтрүүлж байсан.
- **`pf` нь жижиг `q` дээр давамгайлна.** `x = 35, q = 0.5` дээр `pf` 0 → 0.01
  болоход `W` 0.4526 → 1.1609 буюу **2.6 дахин**; `q = 5` дээр ердөө +16%.
- **`V`-ийн нөлөө бага:** p75 (0.41 SOL) нь `W`-г ~1%-иар л өсгөнө.
